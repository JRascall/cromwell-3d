# Valve netcode — Source 2 first, Source 1 as the baseline

How Counter-Strike 2, Dota 2 and Deadlock replicate state and reconcile input,
read top-down from the current engine; and what Team Fortress 2's shipped C++
tells us about the parts Source 2 does not expose.

## A note on sourcing, because it is unusual here

Source 2 is not open. But its networking is far more legible than that implies,
because **the wire schema is published by Valve's own binaries and dumped
automatically on every update**. This note uses four tiers and marks all of
them:

| Tag | What it means | Confidence |
|---|---|---|
| **[VALVE-PROTO]** | Read from `SteamDatabase/Protobufs` — protobuf definitions dumped from the shipping CS2 / Dota 2 / Deadlock binaries. **The message and field names are Valve's own**, compiled into the game. | Very high for *structure*. Semantics are inferred from names unless stated. |
| **[VALVE-SDK]** | Transcribed from the Source SDK 2013 tree — the shipping TF2 client/server C++. | Total. It is the code. |
| **[VALVE-PUB]** | Valve's own public statements. | High, but marketing-adjacent and short on numbers. |
| **[COMMUNITY]** | Reverse-engineering projects and parser implementations. | Good on format, since a wrong parser does not parse. |
| **[inferred]** | My reasoning from the above. | Marked every time. |

**The critical distinction:** a protobuf dump proves *what fields exist and what
they are called*. It does not prove what the server does with them. Where this
note says what a field is *for*, it is `[inferred]` unless tagged otherwise, and
it says so inline.

## 1. The shape of the answer

Four problems, and the two engines solve them differently enough that reading
Source 1 first would actively mislead you:

| Problem | Source 1 (TF2) | Source 2 (CS2 / Dota 2 / Deadlock) |
|---|---|---|
| How does the client learn the network schema? | **Compiled in.** SendTable/RecvTable pairs generated by macros; a mismatch is a version incompatibility. | **Sent over the wire.** `CSVCMsg_FlattenedSerializer` transmits the whole schema with a symbol table at connect. |
| What is the unit of input? | One `CUserCmd` per tick. Input is quantised to the tick. | One `CBaseUserCmdPB` per tick **carrying a list of `CSubtickMoveStep`, each with a fractional `when`**. |
| How does the server know what the client saw? | It **reconstructs** it: ping + the client's reported lerp. | The client **tells it**, as explicit `src_tick / dst_tick / frac` interpolation records. |
| How is a shot resolved? | Server rewinds every relevant player and re-runs the trace. | Same rewind, plus **the client asserts what it thinks it hit and where** — `target_ent_index`, `target_head_pos_check`. |

The through-line: **Source 1 makes the server infer the client's view; Source 2
makes the client state it.** Everything else follows from that.

## 2. Source 2's wire protocol

### 2.1 The schema is sent over the wire — the biggest single change

```protobuf
message ProtoFlattenedSerializerField_t {
    optional int32 var_type_sym = 1;
    optional int32 var_name_sym = 2;
    optional int32 bit_count = 3;
    optional float low_value = 4;
    optional float high_value = 5;
    optional int32 encode_flags = 6;
    optional int32 field_serializer_name_sym = 7;
    optional int32 field_serializer_version = 8;
    optional int32 send_node_sym = 9;
    optional int32 var_encoder_sym = 10;
    repeated .ProtoFlattenedSerializerField_t.polymorphic_field_t polymorphic_types = 11;
    optional int32 var_serializer_sym = 12;
}

message ProtoFlattenedSerializer_t {
    optional int32 serializer_name_sym = 1;
    optional int32 serializer_version = 2;
    repeated int32 fields_index = 3;
}

message CSVCMsg_FlattenedSerializer {
    repeated .ProtoFlattenedSerializer_t serializers = 1;
    repeated string symbols = 2;
    repeated .ProtoFlattenedSerializerField_t fields = 3;
}
```

`Protobufs/netmessages.proto` **[VALVE-PROTO]**

Read that carefully, because it is the whole architecture in one message.

Every string is a symbol-table index (`*_sym`), so names are sent once. Each
field carries **its own quantisation**: `bit_count`, `low_value`, `high_value`,
`encode_flags`, and a named `var_encoder_sym` (things like a normal encoder or a
quantised-angle encoder). `serializer_version` means two versions of the same
class can coexist. `polymorphic_types` means a field can hold one of several
sub-serializers chosen at runtime.

**What this buys, versus Source 1's compiled sendtables** [inferred, but the
consequence is direct]:

- A client can connect to a server whose game DLL has fields it has never heard
  of and still parse the stream, because the encoding is described, not assumed.
- Replays are self-describing. This is precisely why third-party Source 2 replay
  parsers exist and work across patches, whilst Source 1 demo parsing needed the
  matching game build.
- Quantisation is a per-field data decision, editable without a protocol
  version bump.

Source 1's equivalent is `SendPropFloat(SENDINFO(m_flPlaybackRate), 8, SPROP_ROUNDUP, -4.0, 12.0f)`
— the same information, but as a **C++ macro compiled into both binaries**
(`baseviewmodel_shared.cpp:564`, **[VALVE-SDK]**). Same idea; the change is
purely *where it lives*, and that is what makes Source 2's version robust.

```protobuf
    optional .CSVCMsg_PacketEntities.outofpvs_entity_updates_t outofpvs_entity_updates = 23;

```

`Protobufs/netmessages.proto` **[VALVE-PROTO]**

The delta-compression skeleton is recognisably Quake's and unchanged in spirit:
`delta_from` names the baseline frame, `baseline` / `update_baseline` manage the
reference state, and the payload is an opaque bitstream. Three things are new
and worth attention:

**`cq_starved_command_ticks` / `cq_discarded_command_ticks` / `cmd_recv_status`.**
`cq` reads as *command queue* [inferred]. The server is reporting, every entity
packet, how many ticks it **ran out of client commands** and how many it
**threw away**, plus a packed per-command receipt array. Both failures are
invisible in Source 1: starving means the server extrapolated your input,
discarding means you sent faster than it consumed. Sending the counts back lets
the client close the loop and self-tune its send rate. [inferred — the field
names are Valve's, the control-loop reading is mine, but there is no other
plausible use for a starved/discarded counter on the downstream packet.]

**`alternate_baselines`, repeated and per-entity.** Source 1 had one baseline
per class. Multiple baselines let a newly-visible entity delta against something
closer than "class default" — cheaper first-appearance cost, which matters when
players stream in and out of PVS constantly.

**`outofpvs_entity_updates` and `non_transmitted_entities`, as separate
channels.** Entities you cannot see are handled explicitly rather than by
omission. In a competitive shooter that is a design decision with teeth: what
the server chooses to send about an unseen enemy is exactly the wallhack
surface. Having a dedicated, presumably minimal channel is how you keep that
under control. [inferred]

### 2.3 Tick rate is negotiated, not compiled

```protobuf

    optional int32  protocol = 1;
    optional int32  max_clients = 10;
```

`Protobufs/netmessages.proto` **[VALVE-PROTO]**; `CSVCMsg_GameSessionConfiguration`
also carries a tick interval.

`tick_interval` is a float sent by the server at connect. In Source 1
`TICK_INTERVAL` is a compile-time constant in the game DLL, and TF2's entire
prediction and interpolation maths is written in terms of `TICKS_TO_TIME` /

`player_lagcompensation.cpp`). Making it a per-session float is what allows one
client binary to play on 64-tick official and 128-tick community servers without
a protocol change — and, more importantly, it is a precondition for §3.

## 3. Subtick — and it is an *engine* feature

```protobuf
message CSubtickMoveStep {
    option (codegen_delta_encoder) = true;

    optional uint64 button = 1;
    optional bool   pressed = 2;
    optional float  when = 3;
    optional float  analog_forward_delta = 4;
    optional float  analog_left_delta = 5;
    optional float  pitch_delta = 8;
    optional float  yaw_delta = 9;
}

message CBaseUserCmdPB {
    optional int32  legacy_command_number = 1;
    optional int32  client_tick = 2;
    optional uint32 prediction_offset_ticks_x256 = 17;
    optional .CInButtonStatePB buttons_pb = 3;
    optional .CMsgQAngle viewangles = 4;
    optional float  forwardmove = 5;
    optional float  leftmove = 6;
    optional float  upmove = 7;
    optional int32  random_seed = 10;
    optional uint32 pawn_entity_handle = 14 [default = 16777215];
    repeated .CSubtickMoveStep subtick_moves = 18;
    optional bytes  move_crc = 19;
    optional uint32 consumed_server_angle_changes = 20;
    optional int32  cmd_flags = 21;
}
```

`Protobufs/usercmd.proto` **[VALVE-PROTO]**

`when` is a float. A button press is not "down during tick N" — it is "pressed at
fraction `when` of tick N", with the view-angle and analog-movement deltas that
had accumulated by that instant. Valve's public framing is that servers know
*"the exact instant that motion starts, a shot is fired, or a 'nade is thrown"*
**[VALVE-PUB]**, and this message is that claim's implementation.

**It lives in `usercmd.proto`, not `cs_usercmd.proto`, and Deadlock's
`usercmd.proto` contains the identical `CSubtickMoveStep` and `subtick_moves`
field** **[VALVE-PROTO]**. So subtick input is a **Source 2 engine capability
available to every game on the engine**, not a CS2 gameplay feature. That is a
load-bearing distinction and it is the kind of thing only the top-down read
gives you — from CS2 alone it looks like a shooter trick.

Three other fields are quietly significant:

- **`legacy_command_number`.** The name says Valve moved off Source 1's
  monotonic command number as the primary identity. `client_tick` plus subtick
  offsets is the model now. [inferred from the name — but `legacy_` is Valve's
  own prefix.]
- **`prediction_offset_ticks_x256`.** A fixed-point (`/256`) prediction offset,
  i.e. how far ahead of the server the client is running, expressed with
  sub-tick resolution. In Source 1 this quantity is derived by the server; here
  the client declares it.
- **`move_crc`.** A checksum over the move. Source 1 has the equivalent
  (`CUserCmd::GetChecksum` CRCs `command_number`, `tick_count` and the rest —
  `game/shared/usercmd.cpp`, **[VALVE-SDK]**), so this is continuity, not
  novelty: it is how the server detects a tampered or corrupted command.

### 4.1 Four interpolation records, not one

`cl_interp`, `sv_interp0`, `sv_interp1`, `player_interp` — each an explicit
`(src_tick, dst_tick, frac)` triple. The client is not saying "my lerp is
100 ms". It is saying **"I was rendering the world at exactly `frac` of the way
from tick `src` to tick `dst`."**

Compare what Source 1 has to do to get the same number:

```cpp
correct += nci->GetLatency( FLOW_OUTGOING );          // measured ping
int lerpTicks = TIME_TO_TICKS( player->m_fLerpTime ); // the client's reported cl_interp
correct += TICKS_TO_TIME( lerpTicks );
correct = clamp( correct, 0.0f, sv_maxunlag.GetFloat() );

int targettick = cmd->tick_count - lerpTicks;
float deltaTime = correct - TICKS_TO_TIME( gpGlobals->tickcount - targettick );
if ( fabs( deltaTime ) > 0.2f )
{
    // difference between cmd time and latency is too big > 200ms, use time correction based on latency
    targettick = gpGlobals->tickcount - TIME_TO_TICKS( correct );
}
```

`game/server/player_lagcompensation.cpp:384-412` **[VALVE-SDK]**

That is an *estimate* built from two noisy inputs — a measured latency and a
client-reported lerp — with a 200 ms sanity check and a fallback when the two
disagree. It is a good estimate. It is still an estimate, and the fallback
branch exists because it is sometimes wrong.

CS2 replaces the estimate with a statement. **[inferred]**, but the field names
leave little room: there is no reason to send `src_tick`/`dst_tick`/`frac` other
than to let the server reconstruct the client's view exactly.

The presence of *both* `sv_interp0` and `sv_interp1` suggests the server-side
entity interpolation is being reported for two distinct entity sets or two
distinct lerp amounts — Source 1 already has that concept, with `cl_interp_npcs`
giving NPCs a longer lerp than players (`c_baseentity.cpp:5893-5913`,
**[VALVE-SDK]**). [inferred]

### 4.2 The client says what it hit

`target_ent_index`, `shoot_position`, `target_head_pos_check`,
`target_abs_pos_check`, `target_abs_ang_check`.

The `_check` suffix is Valve's. **[inferred]** on the mechanism, but the shape
is unambiguous: the client transmits *where it believed the target's head and
origin were at the moment of the shot*, and the server holds its own history to
compare against. This is not the client deciding the hit — that would be
catastrophic — it is the client supplying its claim so the server can measure
the disagreement.

What that enables, none of which Source 1 can do:

- **Diagnose rather than guess.** "Server and client disagreed by 12 units on
  this target's head at this instant" is an actionable measurement. Source 1's
  equivalent is a player saying the game feels off.
- **Detect impossible claims.** A client asserting a head position its own
  received packets could not have produced is cheating, provably.
- **Decide the tie deliberately.** When client and server disagree slightly,
  someone has to lose. Having both numbers in hand makes that a policy choice
  rather than an accident of ordering.

`attack1_start_history_index` / `attack2_start_history_index` index into
`input_history`, pinning the exact entry at which the attack began — so the
shot is bound to a specific recorded view state, not to the command as a whole.

`is_predicting_body_shot_fx` / `is_predicting_head_shot_fx` /
`is_predicting_kill_ragdolls` are the client telling the server which *effects*
it has already played locally, so the server can avoid double-triggering them.
Source 1's prediction system has the same concern, handled quite differently —
see §7.2.

## 5. The games, and what each one tells you

| | CS2 | Dota 2 | Deadlock |
|---|---|---|---|
| Genre pressure | Sub-100 ms aim duels; hit registration is the product | Hundreds of units, ability timing, no aim | Third/first-person hero shooter — both pressures at once |
| Tick model | Subtick input; 64 Hz official state broadcast **[VALVE-PUB / COMMUNITY]** | Lower state rate; correctness over instantaneity | Subtick present in the protobufs **[VALVE-PROTO]** |
| What it proves | The full input-history + hit-assertion layer is *game* code, in `cs_usercmd.proto` | Source 2 scales down as well as up | **Subtick is engine, not CS2** — the decisive datapoint |

Deadlock is the useful one for this project precisely because it is the *third*
data point. A feature present in both CS2 and Deadlock but defined in
`usercmd.proto` is an engine capability; a feature present only in
`cs_usercmd.proto` is a game decision. That test is only available top-down, and
it cleanly separates "what Valve built into Source 2" from "what CS2 needed on
top". Reading TF2 first would have collapsed both into "netcode".

## 6. The transport — genuinely open source

`ValveSoftware/GameNetworkingSockets` is the real transport layer used by
CS2 and Dota 2, released under a three-clause BSD licence **[VALVE-PUB]**. It
provides reliable and unreliable messages over UDP, message fragmentation and
reassembly, bandwidth estimation, encryption, and P2P/NAT traversal. On Steam it
links against the Steamworks build and gains **Steam Datagram Relay** — routing
game traffic over Valve's backbone rather than the public internet, which is a
latency *and* a DDoS-mitigation play.

The practical point for anyone building this: **the layer everyone
underestimates is the one Valve gave away.** Reliable-over-unreliable,
fragmentation, congestion control and encryption are months of work and are not
where a game's netcode identity lives. The interesting decisions — what to
replicate, when to predict, how to rewind — sit above it and are the parts Valve
did not open. Taking the transport off the shelf and spending the effort above
it is the correct allocation, and it matches this project's existing library
stance in `third-party-library-choices`.

Now the bottom-up half, which is where the *implementation detail* lives,

### 7.1 Entity interpolation

Every networked variable that should be smoothed is registered with a history
buffer:

```cpp
AddVar( &m_vecOrigin,   &m_iv_vecOrigin,   LATCH_SIMULATION_VAR );
AddVar( &m_angRotation, &m_iv_angRotation, LATCH_SIMULATION_VAR );
```

`game/client/c_baseentity.cpp:905-906`

`CInterpolatedVarArrayBase` (`game/client/interpolatedvar.h`, 1591 lines) keeps a
ring of `(changetime, value)` samples and, on each render frame, evaluates at
`curtime - interpolation_amount`. Three behaviours in one class:

- **Linear** between the two bracketing samples (`_Interpolate`).
- **Hermite** across three samples when available (`_Interpolate_Hermite`) — the
  extra sample gives velocity continuity, so a curving trajectory does not
  render as line segments. There is a `looping` flag for cycle-valued variables
  that wrap 1→0.
- **Extrapolation**, explicitly bounded by `cl_extrapolate_amount`, and only
  when *"the server clock got way behind the client clock"* — the comment at
  `interpolatedvar.h:929`. Extrapolation is a failure path, not a feature.

The interpolation delay itself:

```cpp
float C_BaseEntity::GetInterpolationAmount( int flags )
{
    int serverTickMultiple = 1;
    if ( IsSimulatingOnAlternateTicks() )
        serverTickMultiple = 2;

    if ( GetPredictable() || IsClientCreated() )
        return TICK_INTERVAL * serverTickMultiple;      // ← predicted things barely interpolate

    if ( bPlayingMultiplayer || bPlayingNonLocallyRecordedDemo )
        return AdjustInterpolationAmount( this,
                 TICKS_TO_TIME( TIME_TO_TICKS( GetClientInterpAmount() ) + serverTickMultiple ) );
    ...
}
```

`c_baseentity.cpp:5916-5961`

Three things worth taking:

1. **The delay is quantised to whole ticks** (`TICKS_TO_TIME(TIME_TO_TICKS(x))`),
   then **one extra tick is added**. You interpolate between samples you already
   have; the spare tick is the margin for one late packet.
2. **Predicted entities get `TICK_INTERVAL`, not `cl_interp`.** Your own player
   is not interpolated in the past — it is predicted into the future. Two
   entities in the same scene on opposite sides of "now", which is the single
   most confusing thing about client-server games and is here as a two-line
   early return.
3. **NPCs can have a longer delay than players** (`cl_interp_npcs`,
   `c_baseentity.cpp:5893`), walking up the move-parent chain so a child of an
   NPC inherits it. Interpolation delay is per-entity-class, not global.

### 7.2 Prediction

`CPrediction` (`game/client/prediction.cpp`, ~1900 lines) runs the local
player's commands forward locally and reconciles when the server's answer
arrives. The core loop is `PerformPrediction` → `RunSimulation` →
`RunCommand`, with `ComputeFirstCommandToExecute` deciding how far back to
resimulate.

Reconciliation is deliberately *soft*:

```cpp
VectorSubtract( predicted_origin, origin, delta );
len = VectorLength( delta );
if ( len > MAX_PREDICTION_ERROR )
{
    len = 0;                       // A teleport or something, clear out error
}
else if ( len > MIN_PREDICTION_EPSILON )
{
    player->NotePredictionError( delta );
}
```

`prediction.cpp:170-183`

An error is not corrected by snapping. It is *noted*, and then bled off over
time — `GetPredictionErrorSmoothingVector` is added to the eye position in
`CalcPlayerView` (`baseplayer_shared.cpp:1632-1634`). And a large error is
treated as a teleport and **discarded entirely**, because smoothing a teleport
would drag the camera across the map.

Note the two guards, which recur everywhere in this codebase: cosmetic
smoothing runs only `if ( !prediction->InPrediction() )`, and
`IsFirstTimePredicted()` gates anything that must happen once per command
rather than once per resimulation (used for sounds, effects and the haptics
call in `SendWeaponAnim`, `basecombatweapon_shared.cpp:1221`). Getting either
wrong produces duplicated effects or feedback loops, and both are hard to see.

### 7.3 Lag compensation, in full

This is the part you asked about, and TF2's implementation is complete and
readable: `game/server/player_lagcompensation.cpp`, 27 KB.

**Recording.** Every tick, post-think, one `LagRecord` per player is pushed onto
a per-player linked list, and records older than `sv_maxunlag` (default 1.0 s,
hard-capped at 1.0) are dropped from the tail:

```cpp
record.m_flSimulationTime  = pPlayer->GetSimulationTime();
record.m_vecAngles         = pPlayer->GetLocalAngles();
record.m_vecOrigin         = pPlayer->GetLocalOrigin();
record.m_vecMinsPreScaled  = pPlayer->CollisionProp()->OBBMinsPreScaled();
record.m_vecMaxsPreScaled  = pPlayer->CollisionProp()->OBBMaxsPreScaled();

for ( layerIndex = 0; layerIndex < layerCount; ++layerIndex )
{
    record.m_layerRecords[layerIndex].m_cycle    = currentLayer->m_flCycle;
    record.m_layerRecords[layerIndex].m_order    = currentLayer->m_nOrder;
    record.m_layerRecords[layerIndex].m_sequence = currentLayer->m_nSequence;
    record.m_layerRecords[layerIndex].m_weight   = currentLayer->m_flWeight;
}
record.m_masterSequence = pPlayer->GetSequence();
record.m_masterCycle    = pPlayer->GetCycle();
for ( i = 0; i < MAXSTUDIOPOSEPARAM; i++ )
    record.m_flPoseParameters[i] = pPlayer->GetPoseParameter(i);
```

`player_lagcompensation.cpp:313-337`

**This is the detail that separates a working implementation from a broken
one.** It does not record a position — it records the **animation pose**: every
overlay layer's sequence, cycle, weight and order, the master sequence and
cycle, and all pose parameters. Hitboxes are attached to bones, bones come from
the animation, so rewinding position without rewinding animation puts the boxes
in the wrong place on a correctly-positioned player. A leaning, reloading or
crouching enemy is exactly where the difference shows.

There is a deduplication guard — a new record is skipped if the player's
simulation time has not advanced (line 300) — so a still player does not fill
the buffer.

**Rewinding.** `StartLagCompensation` computes the target tick (§4.1's excerpt),
then for each other player walks the history from the head backwards to find the
bracketing records, **interpolating between them** rather than snapping to the
nearest:

```cpp
frac = ( flTargetTime - record->m_flSimulationTime ) /
       ( prevRecord->m_flSimulationTime - record->m_flSimulationTime );
Assert( frac > 0 && frac < 1 );   // should never extrapolate
ang = Lerp( frac, record->m_vecAngles, prevRecord->m_vecAngles );
org = Lerp( frac, record->m_vecOrigin, prevRecord->m_vecOrigin );
```

`player_lagcompensation.cpp:520-526`

The animation interpolation is more careful still, and the reasoning is in the
comments:

- **Interpolation is refused across a sequence or order change** — *"We can't
  interpolate across a sequence or order change"* (line 716), and if the master
  sequence changed, *"all layers will be invalid too"* (line 651). Blending
  cycle 0.9 of a run into cycle 0.1 of a reload is meaningless.
- **Cycle wraparound is handled explicitly:** if the older record's cycle is
  *higher* than the newer's it wrapped, so it lerps to `cycle + 1` and unwraps
  — *"add one to the newer so it is lerping from .9 to 1.1 instead of .9 to .1"*
  (lines 718-723), with a second guard so `.9 → 1.2` does not land at `1.05`.
- **Pose parameters are not lerped at all** — *"don't lerp pose params, just
  pick the closest"* (line 678), with the lerping version left commented out
  beside it.

**Bailing out.** The walk aborts if the player was dead in any record
(`LC_ALIVE`), or if consecutive records differ by more than
`sv_lagcompensation_teleport_dist` (64 units) — *"lost track, too much
difference"* (line 482). You cannot rewind through a teleport, so it declines
to try.

**Restoring.** Changed players are flagged in a bit vector, the pristine values
are kept in `m_RestoreData`, and `FinishLagCompensation` puts everything back.
`sv_lagflushbonecache` invalidates the bone cache on both ends of the move,
because stale bones are exactly the failure this system exists to prevent.

**Culling — and it is this project's own rule.**

```cpp
// get max distance player could have moved within max lag compensation time,
// multiply by 1.5 to to avoid "dead zones"  (sqrt(2) would be the exact value)
float maxDistance = 1.5 * pPlayer->MaxSpeed() * sv_maxunlag.GetFloat();

if ( vHisOrigin.DistTo( vMyOrigin ) < maxDistance )
    return true;
// ... otherwise a view-cone test
```

`game/server/tf/tf_player.cpp:20129-20139`

A cheap radius test derived from *how far anyone could possibly have moved in
the rewind window*, then a cone test, before doing any of the expensive
backtracking. That is CLAUDE.md's **"cull cheaply before testing expensively"**
verbatim, in a shipped game, on the server's hottest path. TF2 also
short-circuits on `pEntityTransmitBits` — *"If this entity hasn't been
transmitted to us and acked, then don't bother lag compensating it"* (line
20125), which is both a performance win and a correctness statement: you cannot
have shot at something you were never sent.

Gameplay is allowed to override all of it — a Medic's heal beam lag-compensates
teammates, and only the current heal target (lines 20087-20102).

## 8. The delta, stated plainly

| | Source 1 (TF2) | Source 2 | Why it changed [inferred] |
|---|---|---|---|
| Schema | Compiled sendtables | `CSVCMsg_FlattenedSerializer` over the wire | Version tolerance; self-describing replays |
| Tick rate | Compile-time `TICK_INTERVAL` | `tick_interval` float per session | One binary, many server configurations |
| Input granularity | One command per tick | `CSubtickMoveStep` with fractional `when` | Tick rate stops being a fairness variable |
| Client view state | Server estimates from ping + reported lerp, with a 200 ms fallback | Client sends `src_tick / dst_tick / frac` | Removes an estimate from the hit path |
| Hit resolution | Server rewinds and re-traces | Same, plus client-asserted `target_*_check` | Measurable disagreement; provable impossible claims |
| Queue health | Invisible | `cq_starved` / `cq_discarded` / `cmd_recv_status` returned every packet | Closes the control loop on send rate |
| Baselines | One per class | `alternate_baselines`, per entity | Cheaper entity first-appearance |
| Transport | Custom, in-engine | GameNetworkingSockets + SDR, **open source** | Commoditised the part that is not differentiating |

**What did *not* change** is as informative. Delta compression against a named
prior frame, per-field quantisation, client-side prediction with soft error
correction, entity interpolation in the past, and server-side rewind for hit
resolution are all present in both. The 2001 architecture is intact; Source 2
replaced the *estimates* with *measurements* and moved the schema from
compile-time to runtime.

## 9. What this means for `cromwell`

Judged against RTS / FPS / third-person, per `cromwell-engine-target-genres`:

**Take now, cheaply:**

1. **A runtime schema, not compiled sendtables.** If networking is ever added,
   describing fields in data — name, bit count, range, encoder — rather than in
   macros is the decision that is expensive to reverse. It also gives replay and
   tooling for free. This is the single highest-leverage thing in this note.
2. **Interpolation delay as a per-entity-class property**, quantised to ticks
   plus one tick of margin. Two lines in Source 1, and it lets a 200-unit RTS
   crowd sit on a longer delay than an FPS player without a second system.
3. **The predicted/interpolated split as an explicit concept.** Your own avatar
   lives in the future; everything else lives in the past. Encoding that in the
   entity model rather than discovering it later is what stops the confusion.

**Design for, do not build yet:**

4. **Record the pose, not the position.** If lag compensation is ever needed,
   §7.3 is the specification, and the animation-layer recording is the part
   everyone omits and then cannot debug. Note the dependency: it requires the
   animation system to be *sampleable and restorable at an arbitrary past time*,
   which is a constraint on the animation architecture, not the network one.
   Worth knowing before ozz-animation is wired in, per
   `third-party-library-choices`.
5. **Subtick input as a data model.** Even single-player, timestamping input
   with a sub-frame fraction rather than bucketing it to the frame is strictly
   more information, and it is nearly free at the point of capture. It is
   expensive to add later because every consumer assumes bucketing.

**Take off the shelf:** the transport. GameNetworkingSockets, BSD-licensed
(§6). Writing reliable-over-UDP is not where this project's value is.

**And the general lesson, which is not about networking.** Source 1 spends real
complexity *inferring* what the client saw — a latency measurement, a reported
lerp, a divergence check, and a fallback for when they disagree
(`player_lagcompensation.cpp:405-412`). Source 2 deletes all of that by having
the client say it. **The cheapest way to know something is usually to have the
party that already knows it tell you, rather than to reconstruct it from
evidence.** That applies directly to this codebase's derived caches: the
`kNeedsTile` escape hatch in `OcclusionGrid` is the same move — do not infer
whether a cell is complicated, record that it is.
